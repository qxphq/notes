# I vibecoded 70k LOC with DeepSeek and let Opus review it.

Since DeepSeek Flash 4.1 was released in September 2026, I've used it exclusively for everything, constantly wondering how much I miss out on by not using the "frontier" models.
I don't really care which model to use and am merely pursuing the lowest price/value ratio, and every problem I threw at DeepSeek was solved well enough to make me happy, so that at no time did I have to ask the "frontier" to save my ass.

Last week I ran out of tasks on this project and decided to get a Claude subscription for a month to sic the Opus dogs on my project, in the hope that the reviews will provide interesting insights.

I am sharing these insights as is, with as little input from me as possible.

## The Project

The project I've built is my replacement for Apple Photos, rebuilt the way I think a photo library should work: a photo library manager with AI-classified photos for easy discoverability and a built-in photo editor.
Self-hosted, running entirely on my own hardware, shipped as an installable PWA.

To give a better idea of the complexity of the project, a few details:

- One Rust service (Axum) serves a statically built SvelteKit frontend.
- SQLite holds the metadata.
- Masters stay in a plain `YYYY/MM/DD` date hierarchy, and every derived file (thumbnails, previews, transcodes) is regenerable. 
- Supports JPEG, PNG, WebP, AVIF, TIFF, HEIC, and develops RAW masters.
- Transcodes video to browser-playable H.264.
- Runs face detection and recognition on the CPU, fully offline, on pinned ONNX models.
- Offline reverse geocoding from bundled GeoNames.
- One OpenAI-compatible vision endpoint generates a short English title and lowercase tags for every imported photo. (I am using a local LLM for that).
- Search is a plain substring AND over tags, locations, camera names, and so on.
- The editing stack: geometry control (lens correction, perspective correction, tilt, crop), tone-mapping, film filters, denoising, sharpening, all possible exposure corrections, and an HDR merge of 2–9 exposures.
- Bulk operations for export, sharing, deletion, hiding, geotagging from a GPX file, and much more.
- WebDAV-based import (compatibility with PhotoSync).

## How it was built

First things first: I did not look at a single line of the code, because I decided to shift my attention to invariants (data integrity, snappy UI, backups, etc.)

So what I did write was a prose spec of what I want to get from the LLM in the end, describing the architecture, setting the tech stack, and defining some invariants, ingrained into the guideline docs (AGENTS.md, SPEC.md):

<details>
<summary>Excerpt from AGENTS.md</summary>

```text
- Simplicity and predictability over UX: on unexpected behavior, return errors or
  panic: terminate straightforwardly, never try to be smart.
- Complexity is a cost, not a feature. Do not add a derivative, cache, abstraction,
  configuration knob, or fallback for a speculative need. Add it only for a
  demonstrated requirement whose benefit clearly outweighs the extra state, code
  paths, and failure modes. When two designs meet the requirement, choose the
  simpler one. Machinery for hypothetical scale or future needs is out of scope.
- Local-first, intended for one small deployment. No scale beyond that is a design input.
- Zero query-time magic: all enrichment and token resolution happens at import.
- One module owns each invariant. No provider traits or plugin systems.
- Parameterized SQL only. SQL statements live in the store layer, nowhere else.
- Document structure in code: every module starts with a //! header (responsibility,
  invariants owned, collaborators). /// doc comments on public items and non-obvious
  invariants. Inline comments only where the reason is not visible in the code.
  Comment the why, never the what. DTOs that cross the frontend/backend boundary
  name their mirror on the other side.
- Rust backend, SvelteKit frontend, Nix flake at repository root.
- Never commit secrets. API keys come from a readable file, never store literals.
```

</details>

The architecture I proposed splits state from function: untouchable master files and regenerable derivatives (the database with aggregations, thumbnails, and other work data) are the state.
Backend + frontend, all the code that touches the state and presents it to the user, is the function.
The state is backed up.
The **function is disposable** as long as its performance satisfies me.

So my job description for those 11 weeks: write the spec and the invariants, triage what the models report, make the product calls.
Writing code was delegated entirely.
Writing rules was not.

## The review framework

To keep the model accountable during its work, I came up with a review framework: one skill plus a concern-scoped brief per axis of the product, and a queue that tracks what has been run.
The LLM reviews its own code along 29 narrow axes, five sections:

<details>
<summary>The 29 axes and the review contract</summary>

- **Correctness and invariants:** import correctness, master and file integrity, sidecar/database mirroring, data model and SQL, search/feed/filters, GPS and GPX geotagging, faces and people, the enhancement stack, the video pipeline.
- **Security and boundaries:** access control and secret hygiene, library isolation, HTTP semantics, the WebDAV drop folder, frontend security.
- **Concurrency, exports, configuration:** locking and async boundaries, export archives, runtime settings.
- **Cross-boundary and frontend:** SPEC/backend/frontend consistency, architecture, UX, visual design, client performance.
- **Code quality:** backend, frontend, test coverage, LLM ergonomics, deslopification, SPEC cleanup, Nix deliverables.

And here is the rough contract every review runs under, from the skill:

- The reviewer gets the whole repo. SPEC and AGENTS.md are the map, and a doc/code mismatch is itself a finding.
- Every finding needs `file:line`, the invariant or contract it violates, and a concrete failure scenario. No style nits, no speculation.
- Findings are reported by severity (critical, major, minor), and the run stops for my triage before anything is fixed.
- Fixes land with a regression test each, behind a scripted check gate, one commit per review.

</details>

Severity is graded by the reviewer.
Triage is mine.

And then, whenever I finished a whole bunch of new features, I would just run the LLM on this review script and let it review the code.

This review framework was applied with DeepSeek **twice** after the product already felt stable.

And then I was done.
Something I had dreamed of for years was here, real and running on all of my devices.
The app just worked.
There was nothing left to do.

## Review with Opus 5.5

And then I got the idea to run the same review pipeline with the frontier model I kept hearing good things about: Opus 5.5, on a $17/month subscription.

Unfortunately, the 5-hour session limits that I kept hitting meant the review had to be split across several days.
Fortunately, none of my sessions were blocked by Opus safeguards.

After a few days, Opus summarized its work:

<details>
<summary>72 findings: 0 critical, 8 major, 64 minor</summary>

```text
- 72 findings across 29 reviews: 0 critical, 8 major, 64 minor. Roughly 2.5 per
  review, about one major per four, and none of the majors was data loss or a
  security breach in the shipped flow.
- Where the majors came from:
  - feature interactions: crop vs. tilt, and the hidden gate vs. `copy-to`,
  - refactors: feed scroll and the bulk-export bug,
  - batch error handling,
  - search edge cases (`day:` windows),
  - performance,
  - one test-coverage gap.
- New core logic (the import pipeline, video and trim, locking, the WebDAV
  reservations) produced almost nothing.
```

</details>

All 72 findings were then fixed by Opus itself.

Now the main question: how severe were the major findings?

The honest answer: the majors were edge cases I hadn't noticed in two months after migrating my whole library into the new app.
So Opus did find real bugs, but subtle ones, in no way blocking.
Not a single finding violated a clearly established invariant, let alone corrupted data.
All findings were rather in the plane of statistical variance inherent to different models, and I wouldn't be surprised if DeepSeek itself would find most of them in the same review round. But even if we assume DeepSeek would come back with 0 findings, we have all the data we need to compare DeepSeek with the frontier:

Objectively, I had no signal to call Opus' capabilities a leap.

For me personally, findings of this class still don't justify the premium and the imposed throttling.

## What Opus thinks of the model that wrote the code

I also asked Opus to write up its assessment of the model that produced the code it had reviewed.

Here are responses without any modifications.

<details>
<summary>What Opus says the model does well</summary>

1. **Architecture that holds wherever a rule can be checked mechanically.**
   - Strict layering: no SQL outside `store/`, nothing in `lib/ui` imports the API, and no relative imports.
   - Every module carries a header that matches its code.
   - DTOs are mirrored 74/74, and design tokens are used everywhere.
   - Every symbol path in the docs resolves.
   - It writes rules a reviewer can grep, and then keeps them.
2. **Failure-path engineering in the code it knows is dangerous.**
   - One armed `Cleanup` per import exit path, and duplicate re-checks inside the transaction.
   - CAS reservations with RAII release, and crash-safe trim markers.
   - A documented lock order with one owner, and staging directories.
   - Comments that name the exact failure each line prevents.
3. **Security by omission.** No raw HTML, no object URLs, no service worker, constant-time password comparison, secrets only as runtime files, and model and asset hashes pinned exactly. It removes dangerous surfaces instead of sanitising them.
4. **An honest test suite.**
   - About 500 backend tests with no assertion-free ones, and loud skips when models are missing.
   - A stub vision endpoint, a pinned Chromium, and cleanup and boundary cases throughout.
5. **Exemplary commit messages and docs.**
   - Commit messages give cause, mechanism, regression origin and test rationale.
   - SPEC and the AGENTS maps are thorough enough that most reviews could check claims against code in minutes.
6. **It takes feedback well.** Round-2 findings were closed cleanly with tests and doc updates. Round 3 found mostly residue, not repeats.

</details>

<details>
<summary>What Opus says it does less well</summary>

1. **It fixes the case, not the invariant.** It is the most frequent root cause behind the majors:
   - The hidden gate is 17 hand-placed handler calls, with no shared function and no route-level test, and `copy-to` was missed.
   - The tmp-sweep hazard was solved for the edit base but not for the other hard links.
   - Tilt was added to the renderer but not to crop.
   - It reasons well inside one feature and does not sweep sibling call sites when it adds or changes one.
2. **It follows a change through only one side of a boundary.** It shows up in docs, briefs, and across frontend/backend:
   - Dead frontend wrappers were removed but their endpoints were left.
   - An endpoint description outlived its endpoint.
   - The briefs fell behind fixed bugs, and 14 route paths went stale after a move.
   - Constants were mirrored without saying so.
   - "Done" means the code it touched compiles and passes, not that every reference agrees.
3. **It falls back softly despite its own "fail loudly" rule:**
   - A nullable column was hedged with `COALESCE` instead of a NOT NULL constraint.
   - A dozen frontend `catch {}` blocks substitute plausible defaults, one of them with a comment defending the guess.
   - `?` inside batch loops silently skips the rest of a batch.
   - Its instinct is to keep the UI running. The project rule was the opposite, and it didn't always notice the conflict.
4. **It refactors confidently without pinning behaviour.** One tidy-up of Svelte `$derived` broke both feed-scroll preservation and bulk export. Neither had a test, because the happy paths it took for granted were exactly the ones not covered.
5. **It doesn't check numbers or environment claims:**
   - A documented `rustc` floor of 1.85, while the lockfile requires 1.93.
   - A `! grep` assertion that `set -e` can never trip.
   - A 5-second poll masking a real race in the trim test.
   - Each looked checked and wasn't.
6. **It breaks its own small rules, repeatedly:** duplicated literals (`'favourite'`, `'hidden'`, `nonceOf`, map math), logic in route files, and off-token font sizes. These are individually trivial, but they show up in nearly every frontend review.

</details>

And here's Opus' one-line verdict:

> A senior-level, architecture-first engineer that is very strong at designing and documenting a system and at hardening the code it knows is risky, and weakest at the unglamorous sweep: propagating a change to every call site, doc, and mirror, and checking claims it could have run.
> Almost every finding is residue at a boundary, not a design error.


## Conclusion

In this article I presented raw data and facts, with as little subjective input from me as possible.
The conclusion I reached from it: the frontier premium buys reviews that find edge cases two months of daily use hasn't hit.
It did not buy correctness of the core: the import pipeline, the photo editing and management, the parts that could corrupt data, produced no findings.

The open-weight model is fast, cheap, and flexible.
It runs with any harness, and it wrote 70k lines that held up.
The work that moved from me to the model was writing code.
The work that stayed with me was setting the vision and writing the rules, and that is the part I would not delegate to either model.
